
   1. действия

Программа для генерации пары ключей — личного и открытого. Работает как отдельное приложение на компьютере. Задача — чтобы ключи генерировались корректно и безопасно, в соответствии с СТБ 34.101.27 (пп. 5.10, 5.12, 6.2, 6.3).

   2. функции программы

    2.1. Генерация случайных чисел (п. 5.10)

    СЧ.1   — есть генератор случайных чисел (ГСЧ). У него есть источники случайности и способ обработки данных от них. Источники описываются.
    СЧ.2   — для каждого источника оценена энтропия. Способ обработки гарантирует, что для `l` битного числа энтропия данных не меньше `l`.
    СЧ.3   — если нет физического источника, используется минимум два альтернативных (системный + активность пользователя).
    СЧ.4   — обязателен хотя бы один физический источник.
    СЧ.5   — есть процедура статистического тестирования ГСЧ. Тест запускается перед первым использованием и входит в общий список тестов программы.
    СЧ.6   — выход ГСЧ — это результат криптографической обработки данных источников (можно с внутренним состоянием). Внутреннее состояние — критический объект.
    СЧ.7   — есть проверка работоспособности физических источников.
    СЧ.8   — проверяется работоспособность источников. Не прошла проверка — генерация запрещена.

    2.2. Вывод из эксплуатации (п. 5.12)

    ВЭ.1   — есть список критических объектов, после удаления которых работа с программой от имени пользователя становится невозможной.
    ВЭ.2   — в список входят все критические объекты, которые лежат в незашифрованном виде.
    ВЭ.3   — в список входят все критические объекты.
    ВЭ.4   — есть сервис принудительной очистки. Он критический, доступен владельцу объектов (возможно, администратору). Если вызван в сеансе владельца — сеанс завершается сразу после очистки.
    ВЭ.5   — очистка идёт без задержек и отступлений.
    ВЭ.6   — очистка пишется в журнал аудита.

    2.3. Настройка среды (п. 6.2)

    НС.1   — определены настройки среды для безопасной установки программы администратором.
    НС.2   — определены настройки для защиты долговременных объектов при хранении. Они должны исключать изменение объектов вне сеансов.
    НС.3   — определены настройки для защиты сеансовых объектов и аутентификационных данных при передаче и обработке.
    НС.4   — отслеживаются уязвимости системных компонентов. При обнаружении — обновление или переход на надёжную версию.
    НС.5   — разрешена установка только тех программ, целостность и подлинность которых подтверждена.
    НС.6   — запрещена установка дополнительных программ, кроме обновлений самой программы.

    2.4. Доверенный канал (п. 6.3)

    ДК.1   — в руководстве описаны правила настройки клиентской программы и её среды. Правила совпадают с правилами для среды самой программы.
    ДК.2   — клиентская программа тоже должна соответствовать этому стандарту.
    ДК.3   — для уровней 2–4 при входе удалённого пользователя нужно минимум два фактора аутентификации.
    ДК.4   — программа аутентифицируется перед удалённым пользователем. Вероятность обмана — не больше 2⁻⁶⁴.
    ДК.5   — пользователь может завершить сеанс в любой момент. Сеанс сам завершается при неактивности.
    ДК.6   — данные обмена защищены: конфиденциальность, целостность, подлинность. Ключи защиты обновляются в каждом новом сеансе.
    ДК.7   — если ключи защиты строятся от пароля, пароль нельзя вычислить по перехваченному обмену.
    ДК.8   — ключи защиты нельзя вычислить даже после раскрытия долговременных ключей и паролей.
    ДК.9   — ключи защиты нельзя вычислить даже после раскрытия долговременных ключей программы.
    ДК.10   — открытие и закрытие канала пишутся в журнал аудита с указанием клиентской программы.

  

   3. Как выглядит работа

1. Программа запускается, проходит самотестирование.
2. Пользователь входит, получает роль.
3. Программа проверяет источники случайности.
4. Пользователь запускает генерацию ключевой пары.
5. Программа генерирует личный ключ, вычисляет открытый.
6. Личный ключ сохраняется в защищённом виде, открытый — экспортируется.
7. Все критичные действия пишутся в журнал (если уровень 3/4).
8. При необходимости — обновление программы или вывод из эксплуатации.


   4. Что должно быть на выходе

  Работающая программа.
  Руководство администратора и руководство пользователя.
  Описание архитектуры и модулей.
  Результаты тестов (в т.ч. статистических для ГСЧ).
  Заключение по анализу исходных текстов.


   5. Как проверяем

  Тесты генерации ключей на известных векторах.
  Статистические тесты ГСЧ.
  Проверка очистки (после неё объекты не восстанавливаются).
  Проверка работы доверенного канала.
  Проверка аутентификации и разграничения прав.
  Проверка соответствия требованиям пп. 5.10, 5.12, 6.2, 6.3.

6. Этапы

1. Разобраться с требованиями стандарта.
2. Спроектировать модули.
3. Написать `rng` и `crypto_core`.
4. Добавить хранение ключей и защиту объектов.
5. Добавить аутентификацию и состояния.
6. Добавить самотестирование.
7. Реализовать очистку при выводе из эксплуатации.
8. Реализовать настройку среды и доверенный канал.
9. Добавить аудит (если нужно).
10. Протестировать и оформить документацию.

7. Модули, необходимые для реализации

Модуль	Ответственность
rng	Только генерация случайных чисел, источники, энтропия, статистические тесты

crypto_core	Генерация ключевой пары, проверка, арифметика

key_storage	Сохранение, загрузка, шифрование контейнеров

auth	Роли, пароли, права

state	Состояния программы и переходы

selftest	Самотестирование (вызывает rng, crypto_core, key_storage)

env_config	Настройки среды

secure_channel	Доверенный канал

audit	Журнал событий

decommission	Очистка критических объектов

cli	Интерфейс пользователя
